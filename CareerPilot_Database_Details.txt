# Production Database Architecture — AI Job Search & Application Automation Platform

Based on your 33-screen UI plan and the earlier MVP direction, I recommend Supabase with PostgreSQL as the primary database, Supabase Auth for identity, and Supabase Storage for resumes.

The database should support the complete candidate journey: account creation → resume parsing → profile review → job discovery → AI matching → application confirmation → submission tracking → automation monitoring → subscription and usage management.

The key architectural decision is to keep candidate data, job-source data, AI-generated analysis, and application execution records separate, while connecting them through stable UUIDs and foreign keys. This gives you a maintainable MVP without sacrificing the ability to scale.

Recommended stack

## Supabase + PostgreSQL

A relational database with native transactions, JSONB, full-text search, row-level security, and optional vector search.

PostgreSQL

Source of truth for users, resumes, jobs, matches, applications, subscriptions, and audit records.

Supabase Auth + RLS

Authentication and database-level isolation of each candidate's private data.

Supabase Storage

Private resume files, with database records storing storage paths rather than public URLs.

Server-side functions + worker queue

Resume processing, AI matching, scheduled discovery, application execution, retries, and webhooks.

## 1. Database design principles

1. PostgreSQL is the system of record. Do not use a separate NoSQL database for the core application entities.

2. Supabase Auth owns authentication. Reference `auth.users`; do not duplicate password hashes or create a second authentication system.

3. Private candidate data is user-scoped. A candidate must never be able to read or modify another candidate's resumes, matches, applications, or settings.

4. Jobs are shared data. Store a canonical job once, rather than duplicating the same job for every candidate who matches it.

5. Matches are candidate-specific. Store each candidate-job score and its explainable analysis separately.

6. Applications are durable records. Preserve application history even if a job expires or disappears from its source.

7. Automation is auditable. Record consent, attempts, state changes, failures, and external confirmation evidence.

8. AI output is versioned. Preserve the model, prompt version, input references, and output needed to explain a result.

9. Usage is measurable. Use append-only usage events for metering, with subscription limits enforced server-side.

10. Files stay outside the relational database. Store resume binaries in a private Storage bucket and keep their metadata in PostgreSQL.

The schema below assumes a single-candidate account model for the MVP, one or more resume profiles per candidate within plan limits, shared job listings, and application automation that can be paused, restricted, or unavailable.

## 2.2 SQL conventions

* UUID primary keys use `gen_random_uuid()`.

* Timestamps are stored in UTC using `timestamptz`.

* `created_at` and `updated_at` are maintained consistently.

* Monetary values use integer minor units (for example, paise for INR) rather than floating-point values.

* Scores use `numeric`, not floating-point types, where predictable decimal storage matters.

* JSONB is reserved for variable or versioned AI payloads, external metadata, and provider-specific data.

* Foreign keys use restrictive deletion by default for records that must preserve history.

* Cascading deletion is used for dependent, user-owned records where appropriate.

* The SQL targets a Supabase PostgreSQL deployment. Run it through migrations in a development project first.

## 2.12 Final integrity constraints

Add these after all tables exist. They address ownership, uniqueness, and deletion behavior that should be enforced by the database wherever possible.

SQL

```
-- ------------------------------------------------------------
-- A. Ensure a resume belongs to the same candidate as its
--    approved profile snapshot.
-- ------------------------------------------------------------

alter table public.resume_profile_snapshots
  add constraint snapshot_resume_owner_fk
  foreign key (user_id, resume_id)
  references public.resumes(user_id, id)
  on delete restrict;

-- ------------------------------------------------------------
-- B. Ensure a match belongs to the same candidate as its
--    match run. Use RESTRICT/SET NULL carefully to preserve
--    history; ownership must still be checked in write logic.
-- ------------------------------------------------------------

alter table public.job_matches
  add constraint match_run_owner_fk
  foreign key (user_id, match_run_id)
  references public.match_runs(user_id, id)
  on delete set null;

-- ------------------------------------------------------------
-- C. Ensure the application resume belongs to its candidate.
--    This is important because a resume must never be selected
--    from another user's account.
-- ------------------------------------------------------------

alter table public.applications
  add constraint application_resume_owner_fk
  foreign key (user_id, resume_id)
  references public.resumes(user_id, id)
  on delete set null;

-- ------------------------------------------------------------
-- D. Ensure the referenced match belongs to the candidate.
-- ------------------------------------------------------------

alter table public.applications
  add constraint application_match_owner_fk
  foreign key (user_id, match_id)
  references public.job_matches(user_id, id)
  on delete set null;

-- ------------------------------------------------------------
-- E. Ensure consent and attempts refer to applications owned
--    by the same candidate.
-- ------------------------------------------------------------

alter table public.application_consents
  add constraint consent_application_owner_fk
  foreign key (user_id, application_id)
  references public.applications(user_id, id)
  on delete cascade;

alter table public.application_attempts
  add constraint attempt_application_owner_fk
  foreign key (user_id, application_id)
  references public.applications(user_id, id)
  on delete cascade;

-- ------------------------------------------------------------
-- F. Ensure events are associated with the correct application.
-- ------------------------------------------------------------

alter table public.application_events
  add constraint event_application_owner_fk
  foreign key (user_id, application_id)
  references public.applications(user_id, id)
  on delete cascade;
```

Migration correction for `candidate_experiences`: In section 2.5, use a simple nullable `source_resume_id REFERENCES public.resumes(id) ON DELETE SET NULL` and enforce candidate ownership in the trusted write function. Do not execute the earlier composite `candidate_experiences_source_resume_fk` statement as written: its `ON DELETE SET NULL` can conflict with the non-null `user_id`. The remaining composite ownership constraints above are intentional, but test their deletion behavior against your target PostgreSQL version before production migration.

# 4. Row-Level Security (RLS)

## 4.1 Access-control model

Use three distinct access levels:

Candidate

Can access their own profile, resumes, preferences, matches, applications, notifications, and usage information.

Public / authenticated read

Can read explicitly published plan information and eligible job listings. Never expose private candidate data.

Trusted server / administrator

Manages job ingestion, AI execution, billing webhooks, queue processing, source configuration, and privileged operational records.

Important: RLS is not a replacement for authentication or application-level authorization. Supabase service-role credentials bypass RLS, so they must never be included in browser code.

## 4.3 Candidate ownership policies

For candidate-owned tables with a direct `user_id` column:

SQL

```
-- Example: candidate can read and update their own profile.

create policy "candidate reads own profile"
on public.candidate_profiles
for select
to authenticated
using (user_id = (select auth.uid()));

create policy "candidate updates own profile"
on public.candidate_profiles
for update
to authenticated
using (user_id = (select auth.uid()))
with check (user_id = (select auth.uid()));

-- Example: candidate can read their own resumes.

create policy "candidate reads own resumes"
on public.resumes
for select
to authenticated
using (user_id = (select auth.uid()));

-- Example: candidate can create their own resume records.

create policy "candidate creates own resumes"
on public.resumes
for insert
to authenticated
with check (user_id = (select auth.uid()));

-- Example: candidate can update their own resume metadata.

create policy "candidate updates own resumes"
on public.resumes
for update
to authenticated
using (user_id = (select auth.uid()))
with check (user_id = (select auth.uid()));

-- Example: candidate can delete their own resume records.

create policy "candidate deletes own resumes"
on public.resumes
for delete
to authenticated
using (user_id = (select auth.uid()));
```

Apply the same ownership pattern to the other private tables, using the appropriate `user_id` column.

### Additional ownership rules

* `candidate_experiences`, `candidate_education`, `candidate_certifications`, `candidate_skills`: verify the authenticated user's ID.

* `resume_extractions`, `resume_profile_snapshots`: verify `user_id`; validate the linked resume belongs to that user.

* `job_preferences`, `automation_settings`, `notification_preferences`: allow only the owner to read or update.

* `job_matches`, `match_runs`, `job_discovery_runs`: allow only the owner to read; initiate privileged processing through server-side functions.

* `applications`, `application_consents`, `application_attempts`, `application_events`: enforce ownership on reads and candidate-initiated changes.

* `notifications`: allow owners to read and mark their own notifications as read.

* `subscriptions`, `usage_events`: candidate read-only; server-side billing and metering writes only.

* `audit_events`: candidate access should be limited to explicitly user-visible events. Keep internal security events private.

* `automation_jobs`: candidates should not directly create or execute privileged automation jobs. Use server-side functions.

For tables with `user_id`, the common ownership condition is:

SQL

```
using (user_id = (select auth.uid()))
with check (user_id = (select auth.uid()))
```

Use `USING` for existing rows and `WITH CHECK` for inserted or updated row values. For read-only tables, use a `SELECT` policy only.

## 4.5 Supabase Storage policies

Create a private bucket named `candidate-resumes`.

Store objects using a path convention such as:

`{auth.uid()}/{resume_uuid}/{filename}`

Example Storage policies:

SQL

```
-- Private bucket: candidate-resumes
-- Folder 1 must match the authenticated user's UUID.

create policy "candidate reads own resume files"
on storage.objects
for select
to authenticated
using (
  bucket_id = 'candidate-resumes'
  and (storage.foldername(name))[1] = (select auth.uid())::text
);

create policy "candidate uploads own resume files"
on storage.objects
for insert
to authenticated
with check (
  bucket_id = 'candidate-resumes'
  and (storage.foldername(name))[1] = (select auth.uid())::text
);

create policy "candidate deletes own resume files"
on storage.objects
for delete
to authenticated
using (
  bucket_id = 'candidate-resumes'
  and (storage.foldername(name))[1] = (select auth.uid())::text
);
```

Generate short-lived signed URLs only after checking resume ownership. Validate file size, MIME type, and actual file content on the server. Storage policies should be tested alongside the database policies.

### Scheduling recommendations

* Job discovery: schedule according to source limits and the candidate's preferences.

* Match calculation: run after relevant job/profile changes, with deduplication.

* Application processing: use a worker queue with retries and dead-letter handling.

* Source health: periodically check enabled sources.

* Notification digests: schedule according to each candidate's timezone.

* Subscription reconciliation: run periodically and after relevant provider events.

Use a managed queue or durable worker architecture for critical jobs. A simple PostgreSQL queue is adequate for an initial low-volume MVP, provided claims are atomic, retries are bounded, and duplicate work is safe.

# 6. Important production decisions

## A. What should not be stored in the database?

* Plaintext passwords.

* Supabase service-role keys.

* OAuth access or refresh tokens in unencrypted columns.

* Full resume files as database blobs.

* Unnecessary personal data copied from job-source payloads.

* Unredacted secrets or credentials in AI prompts and logs.

* Permanent public resume URLs.

For third-party credentials, use a secrets manager. If user-specific tokens become necessary, encrypt them using a managed key and strictly restrict access.

## B. How to keep the database efficient

* Keep canonical jobs separate from candidate matches.

* Avoid duplicating the full job description in each match.

* Use JSONB for variable AI payloads, not every relational field.

* Keep application events append-only.

* Use a separate queue for expensive processing.

* Use database views or carefully designed RPC functions for dashboard aggregates.

* Paginate job listings, application records, and activity logs.

* Add partitioning for high-volume event tables only after measuring actual table growth.

* Avoid storing every raw provider response indefinitely.

* Apply retention policies to temporary AI payloads and operational logs.

## My final recommendation

Use Supabase PostgreSQL + Supabase Auth + private Supabase Storage as the foundation for your AI job-search MVP. It gives you a relational data model, strong ownership controls, transactional application tracking, and room to evolve without introducing unnecessary infrastructure.

Before handing the SQL to Codex, resolve the noted composite foreign-key deletion behavior and generate migrations in dependency order. Then have Codex implement the schema, RLS policies, typed database access layer, and automated cross-user security tests together—not as separate tasks.

The most important production safeguard is that the browser must never be trusted to authorize an application submission, change subscription entitlements, or bypass candidate ownership. Those decisions belong in trusted server-side code, backed by database constraints and an auditable event history.
