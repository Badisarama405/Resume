# UI Development Plan — AI Job Search & Application Automation Platform

This document translates your complete 33-screen list into a screen-by-screen implementation specification for Codex. It is structured to support frontend development, component creation, routing, form validation, API integration, and end-to-end testing.

The plan covers all 33 screens, including:

* Exact screen purpose and visible UI elements.

* All user actions and their expected interaction points.

* Loading, empty, error, and success states.

* Navigation between screens and contextual actions.

* Application automation safeguards, usage limits, and failure recovery.

* Consistent behavior across onboarding, job discovery, applications, and account settings.

Implementation assumptions: The platform is a candidate-facing web application, optimized for desktop and responsive on mobile. Users can discover and match jobs, manage professional profiles, track applications, and configure permitted application automation. Job-source availability, supported application methods, subscription limits, and automation capabilities must come from backend configuration rather than hardcoded frontend assumptions.

# Cross-screen implementation requirements

These requirements apply across the 33 screens and should be treated as shared development rules rather than implemented separately on each page.

## A. Global application shell

* Use a consistent typography system, spacing scale, color tokens, and component library.

* Provide a shared authenticated navigation shell.

* Show the candidate's account menu and notification access.

* Keep the active navigation item highlighted.

* Support responsive desktop, tablet, and mobile layouts.

* Provide breadcrumbs on nested screens.

* Use consistent button variants for primary, secondary, destructive, and disabled actions.

* Use consistent status badges and icons.

* Display user-friendly error messages.

* Provide accessible labels, keyboard navigation, focus indicators, and appropriate contrast.

* Confirm destructive actions before execution.

* Warn users before discarding unsaved changes.

## B. Routing and access control

* Protect authenticated routes.

* Redirect unauthenticated users to Login.

* Preserve the intended destination after login when appropriate.

* Route users with incomplete onboarding to the next required onboarding step.

* Enforce account ownership for resumes, profiles, jobs, applications, and logs.

* Handle invalid IDs and deleted resources gracefully.

* Revalidate permissions and entitlements on the backend.

* Do not treat hidden or disabled UI controls as a substitute for backend authorization.

## C. Shared components

Build reusable components for:

* App header and navigation.

* Sidebar and mobile navigation.

* Page header and breadcrumbs.

* Primary and secondary buttons.

* Form fields and validation messages.

* Search inputs and filter panels.

* Job cards.

* Match-score indicators.

* Skill chips.

* Status badges.

* Data tables.

* Pagination.

* Empty states.

* Loading skeletons.

* Error panels.

* Confirmation dialogs.

* Toast notifications.

* File upload and progress.

* Timeline and activity events.

* Subscription usage meters.

* Notification items.

## D. Application automation guardrails

* Never submit an application without the required candidate authorization.

* Respect source-specific restrictions and supported application methods.

* Do not fabricate candidate answers, experience, skills, or qualifications.

* Pause workflows when required fields cannot be completed reliably.

* Prevent duplicate submissions where possible.

* Treat uncertain submission outcomes as pending until verified.

* Record submission attempts and their outcomes.

* Respect configured usage limits and subscription entitlements.

* Allow candidates to pause or disable future automation.

* Clearly distinguish a submission attempt from confirmed employer receipt.

* Do not expose credentials, session tokens, or sensitive application data in UI logs.

## E. Data and status consistency

* Use backend-defined status enums rather than inventing independent labels in individual screens.

* Store and display timestamps consistently, including timezone handling.

* Show when data was last refreshed if freshness matters.

* Preserve application history when a job listing expires or disappears.

* Keep match scores associated with the profile and job versions used to calculate them.

* Distinguish user-reported application statuses from externally verified statuses.

* Make retry operations idempotent where possible.

* Use server-side filtering, sorting, and pagination for large datasets.

* Avoid displaying fabricated counts, percentages, or processing progress.

# Codex implementation handoff

The screen list defines the UI scope, but a production-ready codebase also needs a concrete technical contract. Use the following implementation order to reduce rework.

Phase 1 — Foundation

Design tokens, app shell, routing, authentication, shared components, responsive layouts, and global error handling.

Phase 2 — Authentication & onboarding

Screens 1–13, including resume upload, profile review, preferences, and first matching results.

Phase 3 — Job discovery & applications

Screens 14–22, including match analysis, confirmation, submission status, and application history.

Phase 4 — Profile & settings

Screens 23–29, including resume management, automation controls, notifications, and subscription usage.

Phase 5 — System screens & QA
